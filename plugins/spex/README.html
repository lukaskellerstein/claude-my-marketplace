spex 3.0 — the process

Four commands take an idea to merged code: new, plan, implement, review. Four more are for any time. comment takes your words about the spec that is open: a question, or what must change. new-bug puts the fix of a bug next in line. delete takes a spec that is not merged off the list. status prints where the work stopped. This page is one map of the process. Pick a case and watch its path.

Status: the design is approved (2026-11-13), and spex 3.0 is built. The script, the ten skills, the ten agents and README.md match this page, and the tests of the script pass. No real spec has run through it yet: the first real run is the test of the skills. Section 10 lists every decision, what the build decided, and the points that wait for later.

1The whole process on one line

A box is a command you type. A dashed pill is the state of a spec after it. You run new one time for an idea, and the other three one time for each spec. You run /clear between two commands: the state is in the files, never in the chat. The four commands for any time are not on this line. They are on the map.

What you said stays saidYour text is kept word for word. No agent changes a decision of yours. If the code makes it not possible, the run stops and asks you. Only you change it, with comment.
The next command is the approvalThere is no approve. Each reply ends with a digest. When you type the next command, you approve it. To say no, you type comment first.
Who writes a claim never writes its proofOne agent writes what must be true. Another plans the test, a third writes it, a fourth writes the code. A script says when it is done.

2The map: every step and every fork

Time runs from top to bottom. Each column is one actor. A box with pointed ends is a fork: the path splits there. The right column shows what is on disk after a step. A band is one skill. A dashed frame is one part of that skill: one more file, with the name of what it is today. A box outside every frame is in the SKILL.md of the band. A green tag names the agent that does the box. Stop at any time, go on later

You can close the terminal in any box of plan, implement or review. Nothing is kept in the chat. One small file in the folder of the spec keeps the place: status.yaml. While a spec is open, that folder is in the worktree of the spec, and the script finds it there. The file keeps one thing only: the phase, and if it is done. It does not keep a step inside a phase. Case C1 plays it, and case C16 shows status.

# specs/006-delete-old-backups/status.yaml      in the worktree of 006
command: implement
state: started
MomentWhat happens
① The phase startsThe box “Mark it started”: the script writes command: and state: started.
② You close the terminalNothing. The file still says started.
③ You type the same command againThe check of the command lets it in, and the phase runs again from its first box. The files of the first run are still on disk, and each agent reads them. In implement, a task that tasks.yaml marks as done is not built again.
④ The phase endsThe last check of the phase passes. The script writes state: done, and commits what the phase wrote on the branch of the spec. Only then the next command is let in.

Why a phase, and not a step. A step inside a phase is a line of text in the skill. The main agent reads it, and no code can see if the agent did it. The start and the end of a phase are different: the script runs there, so the file is true. spec-kit and BMAD keep the place at the same level.

The state of a spec is in this one file. A spec with no status.yaml is a note. plan, done is a planned spec. implement, done is a built spec. The close writes review, done before the merge, so the base branch gets it: that spec is closed. spec.md has no line for the state.

/spex:status runs no agent. It reads status.yaml of the open spec, and prints the phase and the command to go on. It also names a correction or a comment that is not finished.

📍 006 delete-old-backups · implement · started, not done · 3 days ago

NEXT   /spex:implement specs/006-delete-old-backups   (the phase runs again; a task that is done stays done)

What makes a spec change big

During implement, the decider can say “the spec is wrong”. The change is big and stops for you when it touches one of these three. Everything else is small: an agent corrects the spec, and you read it in the digest of implement. To say no, you type comment before you type review (case C25). Small or big, the plan follows the spec, and the run goes back to “Write the tests”. A new test must be red before any code changes.

It touchesExampleWhy you decide
Something you said: a line of your text, or an answer you gaveYou said “all orders”. The API gives a user only the orders of one shop.No agent changes your decision.
The Success or the “Not this” of the specThe export cannot finish in the request for 200 000 orders.It changes what the spec delivers.
The list of specs: a spec is added, dropped or replacedThe tool must be a CLI. Spec 008, the dashboard, is dropped, and 009 replaces the closed spec 004.A new list of specs is yours to accept.

The decider names one of four causes of a red test: the test, the code, the tasks or the spec. The first three are never yours to answer. A task is done only when the script sees its tests green. A task that stays red after its developer is done goes to the decider at once, and it counts in the same 3 rounds (cases A4, A5 and A13).

A later spec is only a note, and no code exists for it. So a wrong name or a wrong fact in a later note is small: an agent corrects the note at the close (case B2). One change is one question: when you accept a new list in implement, the close does not ask again (case B3).

plan uses the same rule, before it drafts. A note is written at new, when the earlier specs are not built yet. So plan first checks the note against the real code. When it does not fit, the decider sizes it. Small: the analyst corrects the note (case B4). Big: you decide (case A3).

Your words at any time: comment

You can stop a run at any moment: press Esc, or close the terminal. Then you type /spex:comment with your words. It works on the one spec that is open, so it needs no spec name. It answers a question, or it corrects the spec and the plan. It writes no code, and it runs no other command: the reply names the command, and you type it. Cases C23 to C27 play it on the map.

What changed, and why: corrections.md

One file for each spec, never shared. spec.md says what is true now. corrections.md, in the same folder, says how the spec got there. The script writes each entry from the verdict it gets, as spex report does today. The file is in git, so it stays when the close removes the worktree. An entry is open until its work is done: the fix is built, or the script stamped the changed plan. When a chat ends before that, the entry stays open, and the same command, typed again, finishes it.

A test that needs a running environment

spex knows no tool. Your project gives it four scripts and one address in .spex/config.yaml. Case C8 plays it on the map.

env:
  up:     ./scripts/env/up.sh       # start it, or do nothing when it runs
  deploy: ./scripts/env/deploy.sh   # put the code of this folder into it
  check:  ./scripts/env/check.sh    # exit 0 when the app answers
  down:   ./scripts/env/down.sh     # stop it, never delete it
  url:    http://localhost:8080     # where the tests find the app
KeyThe script runs itIf it fails
upAt the start of implement, with the other needsThe run stops for you, before any code is written.
deploy, checkBefore every full test run, so also after each fixIt counts as a red test. The decider names the cause.
downAt the close, when the worktree is removedThe close goes on, and the reply says so.

4Branches and worktrees

Decided: each spec gets its own branch and its own worktree (a second folder of the same repo, on that branch). The script makes both when plan starts, and removes both when the spec is closed. One spec is open at a time: the next one starts when this one is closed. The script commits on the branch of the spec by itself, at the end of each phase. On the base branch it commits only with commit: true in the config.

MomentWhat the script doesWhere the chat works
new, new-bugWrite the notes on the base branch, and commit them with commit: true. Without it, you commit them. A worktree gets only what is committed, so plan refuses a note that is not (case C18).The main folder
plan startsMakes no worktree. You start the session in it: claude -w spex/007-csv-export, and your WorktreeCreate hook makes .worktrees/spex/007-csv-export on the branch spex/007-csv-export, from origin/main after a fetch. A start in any other session is GATE-ENTER, and makes nothing. The first start there runs your setup command one time (install the packages, copy .env).In the worktree, from the start of the session
implement, review, commentFind the worktree of the spec by its branch. All files of the spec are there: the spec, the plan, the tests, the code. The same GATE-ENTER holds.In the worktree
A phase endsCommits what the phase wrote, on the branch of the spec. That branch is its own, so no config line is asked. comment does the same after it stamps the plan.In the worktree
The closeIf the base branch moved: merges it into the branch of the spec, and a developer resolves a conflict. So the spec has the notes with their current numbers. Then the later notes are corrected. If the code changed, every test runs again, and a red test goes to the decider. Then it commits, merges the branch, pulls the base branch, and removes the worktree and the branch.Back in the main folder
delete, for a spec with a worktreeCopies the folder of the spec out of the worktree to .spex/archive/ in the main folder, with the code of the branch as one patch file. Then removes the worktree and the branch. Then takes the note off the base branch, and renumbers the later specs (case C10).The main folder

While a spec is open, the base branch can still change. A teammate merges. Or you type new, new-bug or delete: they write notes and numbers on the base branch, in the main folder. The open spec does not see them until its close. So the close takes in the base branch first, and corrects the later notes after that.

The config lines for git

Four lines of .spex/config.yaml say how spex works with git. /spex:init writes them, from what it finds in the repo.

commit: false     # true: the script commits the notes of new, new-bug and delete on the base branch
base: ""          # the branch a spec starts from and merges into. Empty: the branch of the main folder
close:
  cmd: gh pr create --fill && gh pr merge --squash --delete-branch
worktree:
  setup: npm ci   # runs one time in a new worktree
close.cmdWhat the close does at “Merge”
A commandThe script runs it in the worktree. It pushes, opens the request and merges it. It gets SPEX_BRANCH, SPEX_BASE and SPEX_SPEC.
localFor a repo with no forge: the script merges the branch into the base branch, in the main folder.
EmptyThe run waits. You merge, then you type review again (case C20).

What the worktree test showed

Tested on 2026-11-13, in this repo, in a Claude Code session with the sandbox on: a branch and a worktree made with git worktree add, as the script will make them.

QuestionResultWhat it means for spex
Can a skill move the chat into a worktree?The tool EnterWorktree can. But the machine rule forbids it, and the guard hook (worktree-guard.py) denies every edit into a worktree from a session that started on the main folder, subagents too.No skill moves the chat. The session starts in the worktree: claude -w spex/<spec>. A start anywhere else is GATE-ENTER.
Does an agent that starts after the move work in the worktree?Yes. Its folder and its branch are those of the worktree.No agent gets a path to change into.
Can the chat still change the main folder after the move?No. The sandbox refuses a write there, and git refuses a command that targets the main folder.The close runs sync to merge in the worktree: git that moves only refs (fetch, commit, push) works there. finish (the pull, a local merge, the removal) runs when you type /spex:review in a session on the main folder.
Can the script remove the worktree?Not alone, in a sandbox. Two paths of Claude Code in the worktree are write-protected: .claude/settings.json and .claude/.cc-writes. The removal stops half way.The script checks that the folder is gone. If it is not, the same command runs one more time outside the sandbox, and Claude Code asks you once (open point 50).
Does git ignore .worktrees/spex/?Yes: the repo's .gitignore has .worktrees/, by the worktree contract of the machine.The script writes no ignore line.

Today: spex 2.2 makes no branch. 5A change in one spec, and the other specs

A big idea becomes many specs. After new, every spec is a note. A note becomes a full spec only when its turn comes. So a later spec is written from the real code, not from the first plan. The example: a tool that backs up customer databases, described as a web application, in 8 specs. Press a button to see what a change does. The list is every spec in specs/ that is not closed, in the order of the numbers. roadmap.md shows it as one table. A repo has one list: a second idea adds its specs at the end.

What a spec learned reaches the others atWhoWhat happens
A · the close of a specagent in reviewReads the decisions, corrections.md and the deferred findings of the spec. Corrects the later notes. A new list that you accepted in implement is not asked again. A list change that nobody asked you about is one answer from you.
B · the plan of the next specagent in planReads the note, the lines that point A added, and the real code of the closed specs.
C · you change the ideayou with newnew again only adds: a new spec at the end of the list, with the next number. It never changes or drops a spec that exists. To take a spec off the list, you type delete. To change the spec that is open, you type comment. For a bug in merged code, you type new-bug: its spec is the next one in line (cases C6 and B10).

A closed spec is never rewritten. Its code is merged. When a closed spec must change, the list gets a new spec that replaces it.

7Where the tokens go

Not measured yet. These are the reasons the design rests on. A real run must confirm them before we call it proven.

RuleWhat it saves
A fresh agent for each taskThe context does not grow from task to task. Each agent reads only its own slice.
The script does the checksGates, status and “is it done” cost no tokens. No agent reads a whole file to find one state.
The chat holds ids and resultsNo code and no test body in the main chat. It stays small through a long run.
/clear between the commandsEach command starts empty. The state is in the files.
